RWA METADATA ARCHITECTURE
=========================

Purpose
-------
Keep the Cardano asset easily discoverable in wallets and explorers while
putting the complete RWA record in a durable off-chain document. Do not store
private, personally identifying, or commercially confidential information in
Cardano transaction metadata or public IPFS.

Recommended split
-----------------
1. CIP-25 (transaction metadata label 721)
   Store the small public identity record in the mint transaction:
   - name
   - image
   - mediaType
   - short description
   - a `files` entry for the public RWA manifest
   - optionally, the application-specific `rwaManifest` URI

   This is the compatibility layer for wallets, explorers, and token indexers.
   Every Cardano metadata text/bytestring value is limited to 64 UTF-8 bytes.
   CIP-25 image and description values may therefore be represented as arrays
   of 64-byte text chunks. The UI does this for long image URIs and
   descriptions.

2. Public IPFS manifest
   Pin one JSON file for each version of the public RWA record. The IPFS CID
   is content-addressed, so changing the file produces a new CID. Suggested
   path: ipfs://<CID>/rwa-manifest.json

   The mint page generates `cswap.rwa-manifest/v1`; users do not upload an
   arbitrary JSON document. The shared fields are asset identity, issuer,
   valuation, public image, authenticity proof, and publication declaration.

   Basic Real Estate template:

   {
     "schema": "cswap.rwa-manifest/v1",
     "category": "real-estate",
     "asset": {
       "name": "Harbor View Unit 12",
       "tokenName": "HVU-012",
       "externalId": "PROP-2026-001",
       "description": "Public description of the represented property."
     },
     "issuer": { "name": "Example Issuer Ltd.", "country": "PH" },
     "realEstate": {
       "propertyType": "commercial",
       "publicLocation": "Makati City, Philippines",
       "titleOrParcelReference": "TCT-123456",
       "area": { "value": "125.5", "unit": "sqm" }
     },
     "valuation": { "amount": "250000", "currency": "USD", "asOf": "2026-01-10" },
     "documents": {
       "image": { "uri": "ipfs://<image-CID>", "mediaType": "image/jpeg" },
       "authenticityProof": { "uri": "ipfs://<proof-CID>", "mediaType": "application/pdf" }
     },
     "declarations": { "publicDataApproved": true, "generatedAt": "<ISO-8601 timestamp>" }
   }

   A Collectible manifest uses the same shared fields and replaces
   `realEstate` with:

   "collectible": {
     "type": "artwork",
     "makerOrCreator": "Example Creator",
     "productionYear": 2020,
     "serialOrCatalogueNumber": "CAT-001",
     "condition": "excellent"
   }

   Public documents may be stored on IPFS or Arweave. Store each source URI
   and a content hash in the manifest when an independent verification step is
   needed.

3. Private document store
   KYC, personal data, confidential contracts, and unencrypted reports must
   remain in an access-controlled system. Encrypt data before external storage
   where appropriate. Do not publish these files, their plaintext, or
   predictable hashes of sensitive low-entropy information to Cardano/IPFS.

CIP-25 mint record example
--------------------------
{
  "721": {
    "<policyId>": {
      "<tokenName>": {
        "name": "Northline Solar Project",
        "image": "ipfs://<image-CID>/cover.png",
        "mediaType": "image/png",
        "description": "Short public RWA description.",
        "files": [
          {
            "name": "RWA disclosure manifest",
            "mediaType": "application/json",
            "src": "ipfs://<manifest-CID>/rwa-manifest.json"
          }
        ],
        "rwaManifest": "ipfs://<manifest-CID>/rwa-manifest.json"
      }
    },
    "version": "1.0"
  }
}

CIP-86 updates
--------------
CIP-86 enables an authorized party to update selected token metadata fields
without minting or burning another token. It does NOT require a change to the
current one-shot minter validator because the validator does not inspect
transaction metadata.

At original mint, attach a label-86 oracle assignment. For the current demo,
the admin wallet may be both main and update address:

{
  "86": {
    "assign_metadata_oracle": {
      "<policyId>": {
        "main_address": "<adminAddress>",
        "update_address": "<adminAddress>"
      }
    }
  }
}

Later, the configured update wallet signs an ordinary transaction with a
simple metadata update, for example to move to a new immutable IPFS manifest:

{
  "86": {
    "simple_metadata_update": {
      "<policyId>": {
        "<tokenName>": {
          "rwaManifest": "ipfs://<new-manifest-CID>/rwa-manifest.json"
        }
      }
    }
  }
}

Implementation notes
--------------------
- The browser must never receive an IPFS pinning credential. Blockfrost IPFS
  uses a distinct server-only `BLOCKFROST_IPFS_PROJECT_ID`; it is not the
  Cardano Preprod `BLOCKFROST_PROJECT_ID`. Add an authenticated server upload
  route only after this value is configured.
- The upload route validates PNG, JPEG, and WebP image signatures, a PDF proof
  document, and the generated JSON-object manifest before pinning. The image
  becomes the CIP-25 `image` URI; the proof and generated manifest become named
  entries in CIP-25's `files` array. Add issuer authentication and rate limits
  before public deployment.
- The mint transaction should include both label 721 (CIP-25) and the initial
  label-86 oracle assignment.
- The update page should require the connected Eternl address to match the
  configured CIP-86 update address before constructing an update transaction.
- CIP-86 remains proposed. Preserve a complete, useful CIP-25 baseline for
  wallet and explorer compatibility; CIP-86-aware clients can resolve newer
  manifest pointers.
- CIP-68 is the alternative for future assets when metadata must be readable
  by Plutus validators or governed directly on-chain. It requires a new
  reference-NFT/user-token issuance architecture and cannot be retrofitted to
  existing one-shot assets.
